# Лабораторна робота № 4

Тема: Конструювання класів: інкапсуляція та принципи SOLID

Проєкт: PharmacyStock
Варіант: 19
Предметна область: Облік ліків і рецептів в аптеці

## 1. Основні сутності

| Сутність | Роль | Незмінність | Інваріант |
|---|---|---|---|
| Prescription | Рецепт пацієнта | Ні, змінний агрегат | Id > 0, PatientId > 0 |
| PrescriptionItem | Лікарський препарат у рецепті | Так, record | Quantity > 0, UnitPrice >= 0 |
| Patient | Пацієнт аптеки | Так, record | Id > 0, ім'я не порожнє, Email містить @ |
| Medicine | Лікарський препарат на складі | Ні, кількість змінюється | Stock >= 0, Price > 0 |

## 2. Стани рецепта

| Поточний стан | Новий стан | Умова переходу |
|---|---|---|
| New | Approved | У рецепті є хоча б один препарат |
| New | Cancelled | Скасування дозволено |
| Approved | Dispensed | Рецепт підтверджено |
| Approved | Cancelled | Препарати ще не видано |

Стани Dispensed та Cancelled є кінцевими.

Повернення з Dispensed до New заборонене.

## 3. Правила роботи класів

PrescriptionItem створюється з правильними даними
та після створення не змінюється.

Patient зберігає дані пацієнта.
Ідентифікатор, ім'я та електронна пошта перевіряються
під час створення об'єкта.

Prescription містить приватний список препаратів.
Додавання препаратів дозволене лише у стані New.

Стан рецепта не можна змінювати безпосередньо.
Для переходів використовуються окремі методи.

Medicine містить інформацію про препарат.
Кількість препарату на складі не може бути від'ємною.

## 4. Використання принципів SOLID

SRP - кожен клас має одну основну відповідальність.

OCP - нові правила ціноутворення додаються
через нові класи без зміни існуючих.

LSP - архівний рецепт не успадковує звичайний рецепт,
якщо не підтримує всі його операції.

ISP - для зберігання та сповіщень
використовуються окремі інтерфейси.

DIP - сервіс отримує сховище та політику розрахунку
через конструктор.
